# Architecture Decision Records

Each decision: context → decision → consequences. New decisions are appended; an
outdated one is marked *Superseded by ADR-xxx*, never deleted.

## ADR-001 Modular monolith, not microservices (2026-10-24)
**Context.** One developer-owner, one pharmacy at start, many future tools that share
items, suppliers, stock and users.
**Decision.** One deployable application, split into modules (`core`, `catalog`,
`inventory`, `purchasing`, …) with one shared database. Modules talk through service
functions, never by reaching into another module's tables for writes.
**Consequences.** Simple deploy/backup/debug; transactions span modules (approve invoice
+ stock + cost + audit atomically). A module can be extracted into a service later if
load or team size demands it; the API contract stays the same.

## ADR-002 SQLite on the pharmacy node now, PostgreSQL centrally later (2026-10-24)
**Context.** The owner needs the system on the pharmacy Windows PC, working offline
(internet in Egypt drops). The build environment for this phase also blocks PyPI, so no
PostgreSQL driver could be installed or tested here.
**Decision.** SQLite (WAL, `synchronous=FULL`, foreign keys on, `BEGIN IMMEDIATE` for
writes). SQL kept close to ANSI; no SQLite-only features in business logic except
triggers that enforce append-only tables (re-implementable in PostgreSQL).
**Consequences.** Zero-admin install, one-file backup (`manage.py backup`, online-safe),
full offline. Single writer at a time — fine for one pharmacy with a few users. For the
multi-pharmacy SaaS: central PostgreSQL + per-node sync (uuid7 ids make that possible).
**Revisit when:** first second-pharmacy customer, or >5 concurrent writers.

## ADR-003 Money and percentages as integers (2026-10-24)
Money = INTEGER piasters (1 EGP = 100). Percent = INTEGER basis points (12.5% = 1250).
Unit cost (needs fractions of a piaster) = Decimal string, 6 dp, computed with
`decimal.Decimal`. No floats anywhere in financial paths.

## ADR-004 UUIDv7 identifiers (2026-10-24)
Time-ordered (index friendly) and globally unique, so records created offline on
different devices/branches never collide when synced.

## ADR-005 Immutable stock ledger + moving weighted average cost (2026-10-24)
`stock_movements` is append-only (DB triggers reject UPDATE/DELETE). Corrections are
reversing movements. `stock_balances` is a cache updated in the same transaction and
provably consistent (`inventory.verify_balances`, `manage.py verify`). Cost method:
moving weighted average per item per branch. Batches (تشغيلات) are first-class with
their own expiry and public price (Egyptian price rises: old batches keep old legal price).

## ADR-006 Bonus stock is free stock (2026-10-24)
Paid qty + bonus qty both enter stock; the line amount is spread over all of them, so
bonus lowers unit cost. Invoice-level extra discount/tax is allocated to lines
proportionally to line value.

## ADR-007 AI reads, never decides (2026-10-24)
Vision model output is tagged `source=ai`, confidence capped at 0.9; any field < 0.8
blocks approval until a person confirms it. Matching, arithmetic, totals reconciliation
and stock posting are deterministic code. Only the invoice image is sent to the AI
provider (no customer/patient data). Metered per organization via `usage_counters`.

## ADR-008 Matching levels (2026-10-24)
barcode → supplier code → learned alias → fuzzy. Fuzzy matches become `auto` only when
name ≈ identical AND strength, form, pack count, pack content and modifiers (Extra, XR,
Forte…) all agree; otherwise `suggested` and a human must click. Aliases are learned
only from human confirmations, per supplier.

## ADR-009 Session tokens, not JWT (2026-10-24)
Opaque random tokens; DB stores only SHA-256. Instant revocation (logout, password
change revokes all, org suspension kills sessions). Browser: HttpOnly SameSite=Strict
cookie + required `X-Requested-With` header for writes (CSRF). Mobile/integrations:
`Authorization: Bearer`. Passwords: scrypt (stdlib), parameters stored per hash.

## ADR-010 Entitlements are central and platform-controlled (2026-10-24)
`org_entitlements` + `usage_counters` decide which tools an org can use and AI limits.
Tools call `require_feature` / `consume_usage`; none implements its own subscription
logic. Only the platform operator (CLI now, admin console later) can change
entitlements — a pharmacy owner cannot grant himself features.

## ADR-011 No frontend build chain (2026-10-24)
Vanilla JS modules + CSS, strict CSP (`script-src 'self'`, no inline). Maintainable by
one person, nothing to break on dependency updates. Revisit if the UI grows beyond ~5
complex screens.

## ADR-012 Clinical content only from licensed, versioned sources (2026-10-24)
No dose, interaction or contraindication is written from memory or generated by an LLM.
The safety engine stores each fact with its source, source version and review status;
an unreviewed rule cannot fire as "safe". See `CLINICAL_DATA_SOURCES.md`.

## ADR-013 One "demand signal" model for all expected needs (2026-10-24, design only)
Customer requests for unavailable items (F15), the staff shortages notebook (F16-1) and monthly
regimens (F8) are all *expected need*, not purchase orders. They will share one table
(`demand_signals`: item or free-text + ingredient/strength/pack, qty, source, status
open→fulfilled/cancelled, due date, optional customer) read by procurement. Purchase orders
(F9) are a separate entity created only by an explicit approval. Prevents three parallel lists.

## ADR-014 Contact consent is recorded once per customer and channel (2026-10-24, design only)
`contact_consents(customer, channel: phone|whatsapp|sms, granted_at, revoked_at, by)`. Every feature
that contacts customers (F8 reminders, F15 "item arrived") checks it. Only the minimum contact
data is stored; nothing is shared with suppliers.

## ADR-015 New financial records start as drafts (2026-10-24, design only)
Expenses, cash transfers, supplier returns, wallet/InstaPay receipts: created as `draft`, posted
to the existing ledgers (`cash_movements`, `supplier_ledger`, `customer_ledger`, stock ledger)
only on approval by a permitted user, audited. A receipt image is evidence, never proof of payment.

## ADR-016 External channels feed an inbox, never write directly (2026-10-24, design only)
Verified: the official WhatsApp Groups API cannot access existing groups created by personal
accounts nor fetch history; it serves API-created groups of max 8 participants and requires an
Official Business Account. Unofficial tools that log into a personal account are rejected (terms
of service, credential exposure). Therefore: an internal inbox (photo/file upload, quick forms,
optional import of WhatsApp's own "Export chat" file) turns items into drafts routed to the right
module for human review.

## ADR-017 No SQLite planner statistics; reports run off the event loop (2026-11-15)
Found on the pharmacy PC after the real E-Stock import (30,472 items): the stock report took 118 s and
`/api/health` stopped answering for the whole time. `PRAGMA optimize` (daily clean) had stored
statistics while the tables were tiny; after the bulk load SQLite trusted them and scanned whole
tables per row. Decision:
- No `ANALYZE` / `PRAGMA optimize`. Every start (`Database.migrate`) drops `sqlite_stat1`/`sqlite_stat4`
  if present (a restored backup or a manual ANALYZE); dropping changes the schema, so every open
  connection re-plans. The queries are written and benchmarked for SQLite's default plans (keys and
  indexes), which do not depend on table sizes. If a query ever needs statistics, fix the query or
  add an index instead.
- Reports (`/api/home`, sales, stock, profit, transfers, item warnings, invoices, losses, owner reports)
  run in a worker thread on that thread's own connection inside one read snapshot (`Database.read_snapshot`,
  writes refused inside it), so a long report never stops the cashier screen.
Tests: `tests/test_report_freeze_249.py` (fail before the change).

## ADR-018 Refuse the impossible: covered and pending cases (owner 21/11; moved from OWNER_RULES §13 on 26/11)
Rule: `docs/OWNER_RULES.md` §8. Tests: `tests/test_u2_0_refusals.py`.
- Covered (U2-0, 22/11): sale or quantity beyond stock; zero or negative quantity or price; discount above the
  line or invoice value; return above sold minus returned; refund to a card / wallet above what came that way
  (cash for a card invoice = exception); credit sale without a customer; customer collection above the debt;
  supplier payment above the balance (advance = exception); negative drawer counts; supplier invoice dated after
  today; expired expiry at purchase approval (an expiry before the invoice date is always already expired);
  the same supplier invoice number twice. A refund to the customer's own account (store credit) stays allowed
  whatever the invoice was paid with under this rule. ADR-019 adds an owner setting for mixed payments.
  No money leaves the pharmacy. The supplier advance and the cash refund of
  a card invoice can be approved on the screen by the owner or a manager (PIN), with the reason.
- Pending (needs a migration or a later item): an exception path for a genuinely repeated supplier invoice
  number (today always refused), returnable expired goods with permission (today always refused), sale price
  above the public price (the screen cannot type a price; it comes from the batch), a unit change on a line (U2-13).


## ADR-019 Mixed-tender refunds (owner 27/11, #487 and #503)

The owner asked for three organization settings with the #487 recommendations as defaults.
An original-tender refund defaults to card, original wallet channels, cash, then the customer's
account. The owner can reorder the methods or choose proportional distribution across remaining
tender amounts. A setting change also applies to the return side of exchanges.

- Wallet refunds default to confirmed amounts. The owner can allow an unreviewed transfer to
  fund a refund. Rejected amounts and any unconfirmed remainder after a partial approval stay
  excluded. A wallet offset carried into a replacement preserves only its verified portion as verified.
- An explicit store-credit refund on a mixed sale defaults to the original credit part less earlier
  refunds on account. The owner can turn off the cap to allow the full value on the customer's
  account, as in ADR-018. Original-tender refunds still credit only the original credit part.
- The recorded acting shift is shared by every tender row. Migration 0052 preserves the
  register attribution and index from 0050 and ships through the signed in-app update.
