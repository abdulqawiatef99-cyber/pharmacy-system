# منصة إدارة الصيدليات — الوثيقة المركزية

> **ابدأ من هنا.** دي الوثيقة اللي أي أداة تطوير (Claude أو ChatGPT أو مبرمج) لازم تقراها قبل ما تلمس الكود.
> بتلخص الرؤية والحالة والقرارات وخطوة الشغل الجاية. أي مرحلة تخلص لازم الوثيقة دي تتحدث معاها.
>
> آخر تحديث: 2026-10-24

## 1. الرؤية في سطرين
منصة واحدة لإدارة الصيدلية: مشتريات، مخزون، مبيعات، سلامة دوائية، وتحليلات. البداية صيدلية واحدة (صاحب المشروع)،
والمعمارية جاهزة إنها تخدم صيدليات كتير ومخازن وشركات على شكل اشتراكات.
المواصفات الأصلية كاملة موجودة في `docs/specs/` (3 ملفات).

## 2. المبادئ اللي محدش يكسرها
1. **الحسابات حتمية ومُختبرة.** الذكاء الاصطناعي بيقرأ ويقترح ويشرح، لكنه عمره ما يكون المرجع للفلوس أو الكميات أو الجرعات.
2. **مفيش حاجة تأثر على المخزون أو التكلفة قبل اعتماد صريح من إنسان عنده صلاحية.**
3. **دفتر المخزون غير قابل للتعديل.** أي تصحيح بيتم بحركة عكسية، وقاعدة البيانات نفسها بتمنع UPDATE وDELETE.
4. **كل عملية حساسة بتتسجل في سجل التدقيق** (اللي برضه غير قابل للتعديل)، وبتتسجل في نفس الـ transaction بتاعة العملية.
5. **بيانات كل صيدلية معزولة.** كل استعلام بيتفلتر بـ `org_id` جوه طبقة الخدمات، وفي اختبارات بتحاول تخترق العزل ده.
6. **مفيش تخمين.** القيمة اللي مش مقروءة بتتعلم إنها غير مقروءة، وبتمنع الاعتماد لحد ما حد يراجعها. ده بينطبق على الصلاحية والتشغيلة والكميات والجرعات.
7. **مفيش وظائف وهمية.** أي حاجة محتاجة مفتاح API أو جهاز أو بيانات مرخصة بتتكتب بوضوح إنها **غير مُختبرة** لحد ما تتختبر فعلًا.
8. **المحتوى الطبي (جرعات، تداخلات) بييجي من مصادر مرخصة وموثقة بإصدارها**، ومش بيتكتب من الذاكرة.

## 3. المعمارية باختصار
- **نظام واحد مقسم لوحدات (Modular Monolith)**، بلغة Python 3.13. التفاصيل في `docs/ARCHITECTURE.md`.
- **قاعدة البيانات:** SQLite على جهاز الصيدلية (أوفلاين بالكامل). الـ SQL مكتوب قريب من المعيار عشان يتنقل لـ PostgreSQL على السيرفر المركزي بعدين. القرار وأسبابه في ADR-002.
- **الواجهة:** تطبيق ويب PWA بالعربي (RTL)، من غير build ولا مكتبات خارجية، وبيشتغل على الكمبيوتر والموبايل.
- **API:** HTTP/JSON. الدخول يا إما بـ cookie (للمتصفح) أو Bearer token (لتطبيق الموبايل والتكاملات).

```
app/
  core/        المستخدمين، الصلاحيات، الجلسات، سجل التدقيق، الاستحقاقات (الاشتراكات)
  catalog/     الأصناف، الموردين، الباركود، توحيد الأسماء عربي/إنجليزي، محرك المطابقة
  inventory/   التشغيلات، دفتر الحركات، الأرصدة، متوسط التكلفة
  purchasing/  فواتير الشراء: الاستيراد، القراءة الآلية، التحقق، المراجعة، الاعتماد
  api/         طبقة HTTP بس (من غير منطق أعمال)
  web/         واجهة PWA
  migrations/  ملفات SQL مرقمة (ممنوع تعديل أي ملف بعد ما يتطبق)
tests/         اختبارات unittest (من غير مكتبات خارجية)
manage.py      أوامر التشغيل والإدارة
```

## 5. القرارات المعتمدة
كلها بالتفصيل في `docs/DECISIONS.md` (ADR). الأهم منها:
- ADR-001: نظام واحد مقسم لوحدات، مش خدمات منفصلة.
- ADR-002: SQLite محلي دلوقتي، وPostgreSQL مركزي بعدين.
- ADR-003: الفلوس بتتخزن أرقام صحيحة بالقرش، والنسب بالـ basis points، والتكلفة Decimal.
- ADR-004: المعرّفات UUIDv7 (عشان المزامنة بين الأجهزة ما يحصلش فيها تضارب).
- ADR-005: دفتر مخزون غير قابل للتعديل، ومتوسط تكلفة مرجّح.
- ADR-006: البونص بيدخل المخزون ببلاش، فبيقلل تكلفة الوحدة.
- ADR-007: الذكاء الاصطناعي بيقرأ وبس. ثقته أقصاها 90%، وأي قيمة أقل من 80% بتمنع الاعتماد.

## 7. المشكلات المعروفة والمخاطر
موجودة في `docs/PROGRESS.md` ← قسم "المشكلات المعروفة". أهمها:
- كل اختبارات الاستيراد اتعملت على ملفات مصطنعة. فواتير الموردين الحقيقية لسه ما اتجربتش.
- ملفات `.xls` القديمة مش مدعومة (لازم تتحفظ `.xlsx`).
- ملفات PDF اللي فيها نص عربي ممكن ترتيب الحروف يطلع غلط من مكتبة القراءة. محتاج عينات حقيقية.

## 8. الخطوة الجاية بالظبط
1. **محتاج من صاحب المشروع:** ريبو GitHub (Private)، وملف تصدير أصناف من E-Stock، ومن 10 لـ 20 فاتورة حقيقية، وقرار مصدر البيانات الطبية.
2. **بعد كده:** أداة نقل البيانات (المرحلة 2). بعدها تجربة المرحلة 1 على الفواتير الحقيقية، وبعدها البنية التحتية للسلامة (المرحلة 3).

## 9. إزاي تضيف أداة جديدة (إلزامي)
لكل فكرة جديدة: (1) المشكلة اللي بتحلها (2) الوحدة المناسبة ليها (3) البيانات اللي داخلة وطالعة
(4) المكونات الموجودة اللي هتستخدمها، **ممنوع نكرر جداول الأصناف أو الموردين أو العملاء**
(5) تأثيرها على قاعدة البيانات والصلاحيات والأمان (6) التكلفة والاعتماديات الخارجية
(7) معايير القبول والاختبارات (8) تتنفذ كـ migration جديد + وحدة جوه `app/` + اختبارات + تحديث الوثيقة دي.
كل أداة بتتقفل أو تتفتح من خلال `org_entitlements`، مش بمنطق خاص جواها.

**ممنوع أي نموذج ذكاء اصطناعي يعدّل قاعدة بيانات الإنتاج أو قواعد الصلاحيات أو الحسابات مباشرة.**
التعديل بيمشي كده: كود ← اختبارات ← مراجعة ← commit. والرجوع لأي إصدار ممكن من git.
