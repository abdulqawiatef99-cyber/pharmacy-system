## H3 — عالية: سلامة النسخة لا تغطي مرفقات الفواتير كاملة
المكان: app/core/backup.py، create وverify_archive.
التحقق يقارن hash قاعدة البيانات والدفاتر والأعداد ويقرأ ZIP CRC،
لكنه لا يقارن مرفقات الفواتير بsource_files.sha256، ولا يرفض فقد المرفقات المرجعية.

إعادة الإنتاج من قاعدة مصطنعة وفاتورة Excel مولدة في الاختبار:
1. backup.create لإنشاء نسخة فيها DB وملف فاتورة أصلي.
2. إعادة بناء ZIP بنفس DB وmanifest، مع حذف ملف uploads واحد (حالة مستقلة).
3. حالة ثانية: استبدال محتوى ملف uploads مع إبقاء اسمه، وإعادة إنشاء ZIP CRC بصورة سليمة.
4. verify_archive يرجع problems=[] في الحالتين. كنا نتوقع رفض النسخة.

الأدلة: docs/reviews/reproduce_attachment_backup.py.
تشغيل منفصل: python -m unittest docs.reviews.reproduce_attachment_backup -v .
النتيجة: اختباران يفشلان كما هو متوقع على baseline في 0.224 ثانية.
لا يعني هذا أن ملفات حقيقية فُقدت، أو أن عيبًا وقع على جهاز المالك.
لا يدعي الاختبار أن استعادة جزئية حدثت؛ المؤكد أن بوابة التحقق تقبل النقص والتعديل.

المقترح المحدود للمراجعة:
- عند الإنشاء، تحقق من وجود كل source_file مطلوب ومن تطابقه مع sha256/الحجم المسجلين.
- سجل قائمة ملفات النسخة ومسارها النسبي والحجم وSHA-256 وارتباط المصدر في manifest.
- عند التحقق وقبل استبدال قاعدة أو مرفق، تحقق من اكتمال الملفات وأسماء آمنة وأعضاء غير مكررة
  وتطابق hashes مع snapshot DB وmanifest، لا CRC وحده.
- راجع توافق النسخ القديمة format 1/2 قبل اعتماد format جديد. لا تحذف أو تعدل النسخ القديمة.
- لا تستخدم تشفيرًا أو HMAC بلا إدارة مفاتيح معتمدة. hash داخل الأرشيف لا يثبت هوية منشئه
  ضد من يستطيع تعديل DB وmanifest معًا؛ سلامة النسخة والتوقيع/التوثيق مطلبان مختلفان.
- اختبارات قبول: نقص ملف، تعديل محتوى مع CRC جديد، ملفات متنقلة بعد restore، نسخ قديمة،
  فشل القراءة/النسخ قبل الاستبدال، والحفاظ على نسخة الحالة السابقة.

**لم يُنفذ الإصلاح.** تغيير مسار backup/restore يحتاج مراجعة واعتماد؛ لا عمليات إنتاجية.
